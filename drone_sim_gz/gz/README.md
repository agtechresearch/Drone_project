## Estimation = VIO stand-in (changed 2026-10-15 evening)
PX4's simulated GPS has hard-coded 0.2 m / 0.5 m noise and made height/position tracking useless (EKF 0.5 m off, ±0.7 m swings).
The model now carries gz `OdometryPublisher` → gz_bridge publishes `vehicle_visual_odometry` (ground truth, like the real VOXL VIO).
Airframe: `SENS_EN_GPSSIM 0`, `EKF2_GPS_CTRL 0`, `EKF2_EV_CTRL 15`, `EKF2_HGT_REF 3`. Result: hover within ±2 cm, 2 m step settles at 2.00 m.
Without GPS the vehicle has no global origin, so `scripts/run_sitl.sh` sends `SET_GPS_GLOBAL_ORIGIN` after boot (`scripts/set_global_origin.py`);
otherwise the boot-time Hold mode is unavailable and PX4 refuses to arm ("Resolve system health failures").

## Real-vehicle parameters (applied 2026-10-27, source handoff_2026-10-27.zip)
Real Starling 2: VOXL2 M0054, voxl-px4 **1.14.0**, official mass 285 g (ours weighed 2026-11-02: **297.5 g with battery**), MPC_THR_HOVER 0.34, THR_MDL_FAC 0.9, hover ESC ~9300-9700 rpm.
- `make_gz_model.py` airframe now carries the real MPC_* / MC_* / THR_* / COM_* / LNDMC_* / BAT1_* / EKF2 noise values (block "Real Starling 2 parameters"). Motor constant rescaled so the sim hovers at the real command (1.78e-6, 1.78 N/motor max).
- NOT applied: `EKF2_EV_QMIN 1` (gz odometry has quality 0 -> no EV fusion -> no local position, arming denied), `EKF2_EV_CTRL 7` (real fuses EV pos+vel only, heading comes from gyro integration; sim keeps 15 so EKF yaw = truth), `MC_*_CUTOFF` (not in v1.15), CAL_*/TC_*/RC*/VOXL_ESC_*.
- Rotor geometry mismatch to resolve: CAD-derived model and its CA_ROTOR* use fwd ±0.066 / side ±0.088 m; the real CA_ROTOR* say fwd ±0.085 / side ±0.0625 m (axes swapped). Sim keeps the CAD values (they match the physical model). Grid clearances use the CAD side radius 0.148 (real would be 0.1225 -> more clearance).
- Effect in sim: flies, but hover settles with a 3-4 cm steady offset (takeoff reach judgement at h_tol 0.02 times out, mission continues) and sideways legs show roll transients up to ~12 deg (real accel/gain settings). Previous sim-only tuning held <2 cm.
- Real log check (sess170_log102, Offboard -> Land): the v1.14 vehicle keeps its yaw through landing and has no EKF heading resets (delta_heading 0) -> the v1.15 touchdown-spin issue does not affect it.

## Speed ripple along a leg (measured 2026-10-28, ulog ground truth, 9 m legs at 0.45 m/s)
With the real-vehicle gains the vehicle surges at ~0.3-0.4 Hz: ground-truth speed 0.42-0.53 m/s (std 0.022) and a 0.15 m setpoint lag, visible as a stutter in the videos. The offboard stream is position-only (the flight script moves the setpoint in 20 Hz steps, MAVSDK here has no `set_position_velocity_ned`), and PX4 applies `MPC_XY_P` to each step. Experiments (one aisle-A leg each, `scratch ripple_exp.sh`): MPC_XY_P 3.5 (real) std 0.022 / lag 0.15 m; MPC_XY_P 2.0 std 0.014 / lag 0.25 m; MPC_XY_P 0.95 (PX4 default) std 0.008 / lag 0.50 m, max lateral deviation 0.044 m; MPC_XY_VEL_I_ACC 0.4 instead of 0.1 changes nothing (std 0.020). The airframe keeps the real value 3.5; smoother video needs either the default gain (decision: match the real vehicle or not) or velocity feed-forward in the setpoints (real-script change).

## Flight grid (room-local, added 2026-10-19)
The QVIX module is ONE mesh (no named racks), so the grid is derived from mesh slices in `scripts/qvix_grid.py` (geometry constants + table/map/marker generators).
- Rooms: **R1** = south room (model y 0.1–10.1), **R2** = north room (12.3–22.3), vestibule between (partition door x 2.45–3.45, full height). Planning stays inside one room.
- Columns = aisles **A–E** west→east (A 0.1–0.75, B 1.25–2.0, C 2.55–3.3, D 3.8–4.55, E 5.05–5.7 model x; 4 racks 0.5 m wide between). Rows = 1 m bands, row 1 at the room's south end, increasing **northward**. Compass N/E/S/W = room labels = world N/E/S/W; yaw N 0, E 90, S 180, W 270 (same as the flight script `--yaw`).
- Rack tray bottoms at model z 0.3, 0.9, 1.5, 2.1, 2.7, 3.3, 3.8 (7 tiers). Aisle clearance: rotor side radius 0.148 m, swept 0.170 m → side clearance 0.177 (A/E) … 0.227 m (C/D).
- Crossing between aisles only in rows whose rack-free band ≥ 0.8 m: R1 row 10 (band 8.9–10.1, 1.2 m), R2 row 1. Row 1 of R1 / row 10 of R2 have only 0.5 m → no crossing.
- Outputs: `gz/grid/qvix_grid_R1.md` (table: world xy, NED N/E, clearances), `gz/grid/qvix_grid_R1.png` (top view). `scripts/grid_overlay.sh R1 [clear|camera]` draws the cells + labels in the running Gazebo GUI via the `/marker` service (MarkerManager is in PX4's default GUI config; needs the GUI client, not available headless) and aims the camera inside the room. The GUI client can be attached to a headless server later with `gz sim -g`.
- Spawn at a cell: `run_sitl.sh qvix '' <x>,<y>,0.18,0,0,1.5708` with world xy from the table. **Always spawn facing N** (gz yaw 1.5708): a non-north spawn makes the EKF do a heading reset at boot (EV yaw alignment, e.g. 180 deg for S) and PX4 v1.15's auto flight task adds that stale reset delta to its yaw setpoint when `action.land()` first activates it → the vehicle spins ~120 deg on touchdown (4/4 flights on 2026-10-27, ulog `vehicle_local_position.delta_heading` = 180). Facing N = delta 0 = clean landings, and it matches the real Starling 2 (VIO yaw 0 = direction at power-on). `grid_mission.py` enforces this and flies the route's first heading right after takeoff.
- **Grid route flights (added 2026-10-27)**: `scripts/grid_mission.py --route "R1C10:S R1C1 R1C10:N R1D10:E ..."` compiles a cell/heading route into the flight script's MISSION_PLAN (absolute `goto` relative to the spawn cell + absolute `yaw`), rejects diagonal legs, crossings on closed rows and corridors with clearance below `--margin` (default 0.05 m), then imports `path_flight_phase1_v13.py` unchanged, swaps its MISSION_PLAN and runs it with `--sim --csv auto --yaw <spawn heading>` (the "Type Enter" prompt is bypassed). `--check` only prints the plan; `--plan-json` writes the expected stages; `--spawn-pose` prints the gz pose. `scripts/grid_fly.sh "<route>" [gui|headless]` runs the whole thing on the host (SITL restart at the spawn cell → overlay → mavsdk_server → 1 s truth sampler → mission → `scripts/grid_verify.py`), writing `logs/grid_<ts>_{sitl,mission}.log`, `_truth.txt`, `_plan.json`, `_report.txt`. The verifier judges with gz ground truth only: end cell of every goto (via `locate`), max lateral deviation from the corridor centre line during each leg and the remaining clearance to rack/wall, yaw error per turn, landing cell and landing heading (catches the touchdown spin), and failsafe lines in the SITL log → PASS/FAIL. `REUSE_SITL=1` flies on the running SITL (preflight check first; after each landing the script puts PX4 into Hold, because `action.land()` leaves it in Offboard with the signal lost and that blocks the next arming; a long idle on the ground raises `High Accelerometer Bias` and then the script falls back to a full restart automatically). `RECORD=1` records the Gazebo window to `logs/grid_<ts>.mp4` with the GUI camera following the vehicle as a dolly shot (`scripts/cam_follow.py`: odometry subscription → `/gui/move_to/pose` at 20 Hz with a 1 s low-pass on the camera position and 0.3 s on the look-at point; the offset is a fixed WORLD vector `FOLLOW_OFFSET="0,-2.5,1.5"` = 2.5 m south of the vehicle, 1.5 m up, looking north, so the viewing direction never changes; `CAM_FOLLOW_FRAME=body` rotates the offset with the vehicle yaw instead). The QVIX module is made semi-transparent with `/gui/view/transparent` so racks and walls never hide the vehicle (`TRANSPARENT=0` keeps it opaque; the service toggles, so the state is remembered in `logs/.gui_transparent` and cleared when the GUI restarts). `FOLLOW=0` keeps the fixed room camera, `FOLLOW=1` follows without recording. The GUI CameraTracking plugin (`/gui/follow`, `/gui/track`) was tried first, but its follow P-gain cannot be changed from outside and it lagged 2-4 m. In GUI mode the script restarts the Gazebo GUI with `gz/gui_record.config` (same plugins as the world's `<gui>` but no Entity tree, 1900x970 window — the world `<gui>` cannot set the window size and PX4 starts `gz sim -g` without a config) and records only the window region (xwininfo).

## Recording view, GPU rendering, sim speed, parallel instances (2026-10-28 afternoon)
- **GPU rendering.** The GUI used Mesa llvmpipe (~6 fps, ~3.5 cores), which made every camera motion tick. The container has the NVIDIA EGL library but no GLVND vendor file: `gz/glvnd/10_nvidia.json` + `__EGL_VENDOR_LIBRARY_FILENAMES` (set by run_sitl.sh / run_sitl_instance.sh when `/dev/nvidiactl` opens), and `grid_fly.sh` starts the GUI with `vglrun -d egl` (VirtualGL 3.1.5 installed in the container from `/vgl`, plus `libxtst6`). Recording now ~20 distinct fps (25 fps capture). If `/dev/nvidiactl` gives "Operation not permitted" / NVML "Unknown Error", the running container lost its GPU cgroup access: `docker restart starling-gz` (done 2026-10-28).
- **Front camera picture-in-picture.** `gz/gui_record.config` has a floating `ImageDisplay` (480x360, top-right) on `/front_camera`.
- **Overview camera** (`scripts/cam_follow.py`, started by `grid_fly.sh` with RECORD=1 or FOLLOW=1). Default view `aisle`: camera in the same aisle 3.5 m south of the vehicle at a fixed 3.0 m, always looking north; the line of sight runs inside the open aisle, so racks never hide the vehicle (the module is made semi-transparent so the south wall doesn't either). Motion is done by the GUI's CameraTracking plugin (`/gui/track` FOLLOW_LOOK_AT, world-axis offset, smoothed every render frame); the script only steers the offset at 10 Hz over the topic. `/gui/move_to/pose` is not used: it answers only after its ~0.3-0.5 s move animation (2-3 updates/s). Other views: `oblique`, `side`, `chase` (FOLLOW_VIEW). Tuning env: AISLE_BACK, AISLE_Z, AISLE_DIR, FOLLOW_PGAIN, TRACK_PGAIN.
- **Visibility aids.** Orange translucent halo = a visual of the model (`gui_halo`, visibility_flags 2; the front camera has visibility_mask 1 so it never sees it). Height pole + floor ring + 30 s trail are GUI markers drawn by a second `cam_follow.py` process (CAM_FOLLOW_ROLE=markers) through one `/marker_array` call per update (the plain `/marker` service never replies, so each call waited for its timeout). TEXT markers are not supported by ogre2 here. gz python bindings crash with requests from several threads: keep one thread per process.
- **Sim speed.** `SIM_SPEED=2 grid_fly.sh ...` sets `real_time_factor` at runtime (`/world/qvix/set_physics`) and runs the mission on the Gazebo SIM clock: `scripts/sim_clock_udp.py` relays `/world/qvix/clock` over UDP (14600+N) and `grid_mission.py --sim-clock` installs an asyncio loop on it (the flight script itself is unchanged). A fixed x2 clock scale was tried first and failed (RTF sagged under load, the vehicle flew 0.80 m/s instead of 0.45). Truth sampling is 1 s of sim time; screen video is slowed back with setpts; the front-camera video is sim-timed anyway. Achieved RTF depends on host load (the shared host often runs at load 30+ on 32 cores).
- **Parallel instances.** `INSTANCE=N grid_fly.sh "<route>" headless` (N>0) runs a separate Gazebo world (GZ_PARTITION starling_N) and PX4 `-i N` (`scripts/run_sitl_instance.sh`: offboard udp 14540+N, mavsdk_server 50051+N, model starling2_N, private working dir build/px4_sitl_default/instance_N), stopped with `scripts/stop_sitl_instance.sh N`. The global origin is set over the instance's offboard port before mavsdk_server binds it (all GCS links send to the same remote 14550 and PX4 locks onto the first sender), and shell commands use the local PX4 client `bin/px4-<module> --instance N`. Verified: instance 1 headless at x2 flew an aisle-C leg PASS while instance 0 ran with the GUI. `scripts/rtf_watch.py` prints the achieved RTF of a world.

## Workbench, live maps, process hygiene (2026-10-28 evening)
- **Workbench** (`scripts/bench.sh start [cell] | stop | status | ui | cmd "<command>"`): a separate, persistent SITL (instance 1, GZ_PARTITION starling_1, PX4 -i 1, mavsdk 50052) with its GUI on the VNC desktop and a controller `scripts/bench_ctl.py`. In the Gazebo window: play/pause button (the mission runs on the sim clock, so it pauses too), hotkeys in the 3D view (1-9 run preset, R reset, X stop, L loop, P pause), the "Bench command" panel (Message `data: "run 2"` / `"repeat 3"` / `"loop on"` / `"reset"` / `"stop"` / `"list"`, then the Publish switch; the panel always publishes on `/echo`, identical repeats within 2.5 s are ignored), and the "Bench status" panel (Echo switch on; status lines start with ▶). Presets 1-8 = the eight R1 rack-face surveys, 9 = the first C/D grid route. Reset = stop the mission, force-disarm, teleport to the route's start cell keeping the current heading (a heading jump leaves the EV-only EKF with "Yaw estimate error" for > 90 s and arming is denied), wait for `commander check` OK. Each run is judged with ground truth (`logs/bench_<ts>_*`). Everything is started with setsid: closing a terminal or the end of any flight script never stops it; only `bench.sh stop`. Your own script can fly it with `--port 50052`.
- **Live mini-maps** (`scripts/live_map.py`, started by grid_fly.sh in GUI mode and by bench.sh): `/map/face` = the rack face the vehicle looks at (front-camera view, mirrored for W faces) with the vehicle's position/height and the last 60 s of path, `/map/plan` = top-down room plan (north left, east up) with position, heading arrow and path. Shown below the front-camera PiP in gui_record.config and gui_bench.config.
- **Hidden recording display**: `GUI_DISPLAY=:99 grid_fly.sh ...` runs the instance-0 GUI on an Xvfb inside starling-gz (socket visible on the host via the /tmp/.X11-unix bind mount) and records it there, so the VNC desktop stays free for the workbench. Recordings use `-draw_mouse 0`.
- **Process hygiene with several instances**: `stop_sitl.sh` now stops only instance 0 (processes without GZ_PARTITION; `stop_sitl.sh all` = everything); `stop_sitl_instance.sh N` kills every process carrying GZ_PARTITION=starling_N (a leftover clock subscriber made PX4 think the world was still running: "gazebo already running world"). The gz ruby process rewrites its argv into one string: match it with `^gz sim` (an unanchored pattern also matches the launching bash -c line). The origin of every instance is set over its own offboard port (udp 14540+N) and PX4 shell commands go through the local client `bin/px4-<module> --instance N` (all GCS links send to 14550). mavsdk_server starts only after the origin setter released its port.
- **Verifier**: leg altitude is read from the last sample at/before the leg's [END] (with hover 0 the next climb starts at [END]; false altitude errors of 0.12-0.13 m before).
- **Control panel + faster start (2026-10-28 18:45)**: `scripts/bench_panel.py` (Tk, host, always on top over the right side of the workbench Gazebo window): route list, start, pause/resume, reset, stop, repeat N, loop on/off and the controller's last status; started by `bench.sh start|ui`.
