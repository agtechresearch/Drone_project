## 주요 결론

### 1. 스테레오 카메라는 없다 (1차 세션 기록 정정)
`voxl-vision-hub.conf`의 `voa_inputs`에 스테레오 3종(`dfs_point_cloud`/`stereo_front_pc`/`stereo_rear_pc`)이
`enabled:true`로 있으나 **전부 죽은 템플릿 엔트리**. config의 `enabled`는 구독 시도일 뿐 하드웨어 유무와 무관.
- 실제 카메라 4개: `tracking_front`(ar0144 **단안**), `tracking_down`(ar0144 **단안**), `hires`(imx412), `tof`(pmd-tof-liow2)
- MPA 파이프·extrinsics 프레임에 `stereo_*` **0건**
- → **VOA 실입력 = ToF 1개 + 하방 rangefinder.** 커버리지는 **전방 원뿔(106.5°×85.1°, 0.15–6m) + 하방뿐, 측·후방 사각지대.**

### 2. VOA는 돌지만 PX4가 전부 버리는 중
`en_voa:true`로 20Hz `OBSTACLE_DISTANCE` 송신 중인데 PX4 쪽이 전부 공장 기본값:
`CP_DIST=-1`(비활성) / `COM_OBS_AVOID=0` / `MPC_POS_MODE=4`. ModalAI VOA 셋업이 한 번도 적용된 적 없음.

### 3. Offboard에서는 Collision Prevention이 애초에 동작 안 함 → 로드맵 (A) 폐기
PX4 v1.14 문서 원문: *"Set to 0 or 3 to enable Collision Prevention in Position Mode (default is 4)."*
Collision Prevention은 **Position 모드 전용**. Offboard 문서엔 CP·지오펜스 언급 자체가 없음.
→ **단계1-(A) VOA 활성화 경로 막힘. (B) 파이썬 레벨 회피가 유일.**

### 4. `voa_pc_out` = level 프레임 (파이썬 회피의 입력으로 확정)
`voa_manager.c` / `geometry.c` 직독 결과:
- **원점 = 기체 본체**, **롤·피치만 제거(yaw는 헤딩 유지)**, **X전방·Y우측·Z하방**
- 실측: Float XYZ, 12B/pt, ~700pt, 20Hz
- → **이미 기체 상대 + 헤딩 정렬. 포즈 읽어 변환할 필요 없음.** 전방 장애물 = X 큰 값 & |Y| 작은 값
- **z 바운드(±0.15m) 필터는 `voa_pc_out`에 안 걸린다** — PX4 MAVLink 경로(`pie_binner`)에만 적용.
  `voa_pc_out`은 0.15m 복셀 다운샘플만 거친 전체 클라우드 → 우리 필터 직접 설계 가능
- VIO 기반 모션 보상 적용됨. 단 VIO 없으면 항등변환 폴백 → 파이썬에서 VIO 상태 병행 감시 필요

### 5. PX4 레벨 지오펜스는 켜지 않는 게 맞다
`GF_MAX_HOR_DIST=0`, `GF_MAX_VER_DIST=0`(둘 다 비활성), `GF_ACTION=2`(Hold), `GF_SOURCE=0`(GPOS).
수정은 가능하나 — ① `GF_ACTION=2`면 위반 시 **Hold 전환 → offboard 끊김 → 파이썬이 제어권 상실**,
② GPS 없는 VIO-only(`EKF2_HGT_REF=3`)라 전역위치 기반 동작 불확실. → **파이썬 레벨로 복구가 정답.**

### 6. v14 — 지오펜스 복구 완료
**CR 로직을 그대로 이식하면 안 됐다.** CR은 홈 기준 반경 2.5m인데 현 MISSION_PLAN은
`("right", 10.0, ...)`으로 홈에서 10m+ 이동 → **이륙 직후 오발동.**
(CR도 고도 검사는 이미 setpoint 기준이었고, 수평만 홈 기준이라 문제였음.)

→ **두 겹 설계로 재작성:**
| 층위 | 기준 | 기본 |
|---|---|---|
| 1. 추종 오차 펜스 (주 방어선) | 실제 위치 vs **명령 setpoint** (h 2.5m / v 1.5m) | 항상 켜짐 |
| 2. 홈 절대 펜스 | `--max-home-dist` / `--max-alt-agl` | **꺼짐**(0) |

**오발동 방지 3중**: ① `offboard.start()` 성공 후에만 arm, 착륙 진입 시 해제
② 1.0s 연속 위반해야 발동(단발 VIO 글리치 방어) ③ setpoint 점프 시 수렴까지 층위1만 유예 +
30s 내 수렴 실패는 고장으로 간주 발동 (유예 중에도 층위2는 계속 감시).

**부수 확인**: `trigger_emergency_land`의 **kill 폴백은 v13에 이미 있었음** → docs/03 정정, 추가 작업 불필요.

## 주요 결론

### 1. GitHub에는 VOXL SDK가 없다 (조사 방향 자체의 교정)
44개 중 **37개(84%)가 upstream fork**, ModalAI 자체는 7개뿐이고 그중 관련된 건 거의 없다.
`voxl-vision-hub`·`voxl-mapper`·`libmodal-pipe` 등 **SDK 본체는 전부 GitLab**(`voxl-public`).
GitHub에서 `voxl`로 시작하는 저장소는 `Voxl-Plugin` 하나이고 그마저 외부 개인의 GStreamer 템플릿 fork.

### 2. 기체가 돌리는 PX4 소스를 커밋 단위로 특정
기체 실측 `PX4 1.14.0 / git 3e7db37f / Vendor 2.0.133` ↔ `modalai/px4-firmware` 태그 조회 대조:
```
3e7db37f06278a7756531d926d8bac8a71c6555f  refs/tags/v1.14.0-2.0.133-dev
```
**완전 일치.** 태그 명명 규칙 `v<PX4버전>-<Vendor버전>-dev` → 기체 버전으로 항상 역산 가능.
이제 PX4 동작 의문은 추정이 아니라 **실행 중인 그 소스를 읽어서** 답할 수 있다.
(현 1.14 라인은 2.0.146까지 나옴 = 13패치 뒤처짐. ModalAI 주력은 이미 PX4 1.17)

### 3. "CP는 Offboard에 개입 못 함"이 3중 확증 — 단계1-(A) 완전 폐기
| # | 근거 | 출처 |
|---|---|---|
| 1 | PX4 공식문서 문장 | docs.px4.io (2차 세션, docs/04) |
| 2 | **기체 펌웨어 소스**: `CollisionPrevention`이 `FlightTaskManualPosition` **한 곳에서만** 인스턴스화 (Auto·Offboard 경로 전무) | `px4-firmware` v1.14.0-2.0.133-dev |
| 3 | **ModalAI 자체 파라미터 주석**: *"PX4 mainline currently does not support VOA in the default position mode of 4"* | `voxl-px4-params/voa_helpers/` |

추가 구조적 근거: Offboard 셋포인트는 flight_mode_manager를 **거치지 않고** `trajectory_setpoint`로
`mc_pos_control`에 직접 들어간다 → CP가 끼어들 지점이 경로상에 없다.
`src/lib/collision_prevention/`에 구현은 온전히 있다. **코드가 없어서가 아니라 호출 모드가 수동 Position뿐이라 안 되는 것.**

### 4. `voa_pc_out` 파서 근거 완비 — 다음 세션 즉시 착수 가능
`libmodal-pipe` 헤더 직독으로 **와이어 포맷 확정**:
- `point_cloud_metadata_t` = **packed 60바이트** → Python `struct` `"<IqIII32sI"` (calcsize 검산 60 확인)
- 필드: magic(u32) / timestamp_ns(i64) / n_points(u32) / format(u32) / id(u32) / server_name(char32) / reserved(u32)
- 뒤에 `n_points × 12B` float32 XYZ (format 0 = FLOAT_XYZ) — **docs/04 실측(12B/pt)과 정합**
- magic = `0x564F584C`("VOXL") — 카메라·ToF·IMU와 **공용**이라 파이프 이름으로 구분해야 함
  (`px4_vehicle_local_position`은 `0x706F7365`("pose")로 구분 가능)

**MPA 구독 프로토콜**(`client.c`/`server.c` 직독): `/run/mpa/<파이프>/request`에
`이름+%08d난수`를 write → 서버가 `/run/mpa/<파이프>/<그이름>` mkfifo → 그 FIFO를 read.
→ **`libmodal_pipe.so` 링크 없이 순수 파이썬으로 구독 가능** (v14 구조에 그대로 맞음)

⚠️ `libmodal-pipe/python/pympa.py`는 **66줄·IMU/카메라 전용**. 포인트클라우드 미지원 → 우리 용도로 못 씀.

### 5. ModalAI 공식 회피 파라미터 확보 — 우리 임계값 출발점
`voxl-px4-params/params/v1.14/voa_helpers/` 3파일 전문 확보:
| 파라미터 | 실내 | 실외 |
|---|---|---|
| `CP_DIST` (최소 접근거리) | **1.0 m** | **3.0 m** |
| `MPC_POS_MODE` | 0 | 0 |
| `CP_DELAY` / `CP_GUIDE_ANG` | 0.0 / 0.0 | 0.0 / 0.0 |
| **`CP_GO_NO_DATA`** | **1** | **1** |

**`CP_GO_NO_DATA=1`이 핵심 시사점**: ModalAI는 전방 ToF만 있는 이 기체에서
**"센서가 못 보는 방향으로의 이동을 막지 않는" 쪽을 기본으로 택했다.**
→ **측·후방 사각지대에 대한 ModalAI 공식 답은 "보호하지 않음".**
우리가 사각지대까지 방어하려면 ModalAI 기본보다 **더 보수적으로 직접 설계**해야 한다.
(유력안 "정지 후 yaw 스캔"이 이 공백을 메우는 방향이라 타당함이 뒷받침됨)

### 6. 우리 기체 파라미터가 공식값과 일치 (정상성 확인)
`voxl-px4-params/v1.14/platforms/D0014_Starling_2.params` — SKU `MRB-**D0014**-...` 대응.
`EKF2_HGT_REF=3` 등이 **기체 실측값과 일치** → 누가 임의로 바꿔놓은 게 아니다.
이 파일에도, 부팅스크립트(`voxl-px4-start`)에도 `GF_*`·`CP_*`가 **없다**
→ **지오펜스·회피 기본 꺼짐은 ModalAI의 의도된 설계**이고, helper 파일을 별도 적용하는 구조.
우리가 v14에서 파이썬 레벨 지오펜스를 만든 건 이 설계와 어긋나지 않는다.

### 7. `voxl-mapper` 소스 확보 — ToF-only 호환이지만 당장 도입 보류
"미설치"로만 적어뒀던 패키지의 소스(voxblox + ETH loco planner + mav_trajectory_generation).
- **긍정**: `config_file.h`에 `tof_0/1/2` 각각 pipe·enable·rate·extrinsics 정의
  → **ToF만으로 동작 설계**. 우리 제약(스테레오 없음)이 배제 요인이 아니다.
- **부정**: ①README에 *"only authorized for beta usage"* + 책임 면제 명시
  ②`voxl-cross` 도커 빌드 필요 ③출력이 `TrajectoryProtocol`→PX4 경로면
  **우리 파이썬 offboard와 제어권 충돌** (정확한 흐름 미확인)
  ④우리 미션은 지그재그 **커버리지**인데 전역플래너는 A→B 최단경로 목적
- **판단**: v14 실비행 검증도 안 끝난 상태에서 변수 급증 → **당장 도입 안 함.**
  단 `obs_pc_filter.cc`는 ModalAI의 ToF 장애물 필터 참조 구현이라 별도로 읽을 값이 크다.

### 8. 부수 발견 (활용 가치 있는 것들)
- **`voxl-inspect-points`** (`voxl-mpa-tools`) — 포인트클라우드 검사 도구.
  파이썬 짜기 **전에** `voxl-inspect-points voa_pc_out`으로 포맷 해석 검증 가능
- **`px4-flight-review`** (ModalAI 자체, `voxl-dev` 브랜치) — ulog 웹 분석 도구.
  과거 로그의 추종오차 분포로 **v14 임계값을 실비행 없이 검토**할 수 있다
- **`starling_2_indoor_position.params`** — ModalAI 공식 실내 타이트추종 튜닝
  (`MPC_XY_VEL_MAX 3.0`, `MPC_XY_P 3.50`, `MPC_Z_P 5.0`). v14 `--max-horizontal-dev 2.5`
  타당성을 책상에서 1차 판단할 재료
- **HITL 자산**: `voxl-px4-hitl-start`(기체) + `voxl-hitl-vio-server`/`voxl-hitl-rangefinder-server`(SDK)
  → 기체 없이 회피 로직 시험 경로
- **배터리**: `VOXLPM` 드라이버가 SLPI에 빌드돼 있고 `battery_helpers/` 파라미터 존재
  → 저전압 failsafe는 파이썬 구현 전에 **PX4 파라미터로 되는지 먼저 확인**
- **`voxl-mini-tof-server`** = ST **VL53L8**용(우리 ToF는 `pmd-tof-liow2`, 다른 부품).
  단 `docs/`에 **멀티플렉서 자료**가 있어 **측·후방 사각지대를 하드웨어로 메우는 옵션**이 될 수 있음
  — **미검증 가설** (전원·I2C 여유·마운트·extrinsics 확인 필요)
- **VOXL2 PX4는 2프로세서 구조**: 앱(`voxl2`, Linux)엔 MAVLink·navigator·commander·MPA브리지,
  **SLPI DSP(`voxl2-slpi`)에 EKF2·mc_pos_control·flight_mode_manager**. muORB로 연결
- **`px4_vehicle_local_position` 파이프의 정체 확정**: `vehicle_local_position_bridge` 모듈이
  uORB `vehicle_local_position`(=EKF2 출력)을 `pose_vel_6dof_t`로 발행. **MAVLink 미경유**
  → v13이 MAVSDK telemetry 대신 이 파이프를 택한 게 옳은 설계였다는 근거

## 메모 (3차)
- **`git ls-remote`는 GitHub API 한도(60/hr)를 안 쓴다.** 브랜치·태그 조회는 이걸로 할 것
- `--depth 1 --filter=blob:none`이면 539MB 저장소도 ~100MB로 트리 전체 열람 가능
- **fork 저장소의 `master`는 upstream 그대로.** ModalAI 수정은 `voxl-*`/`mai-*` 브랜치와 태그에 있다
  → 브랜치 미지정 클론은 upstream을 읽게 됨
- `PX4-user_guide` fork(2022)·`qgroundcontrol` fork(2019)는 오래됐다. 최신은 docs.px4.io 직접 참조
- `voxl-px4-params`의 `experimental_do_not_use/` 디렉토리는 이름 그대로 쓰지 말 것
- 파라미터 파일 충돌 함정: `starling_2_indoor_position.params`는 `MPC_POS_MODE 4`,
  `voa_enable_*.params`는 `0`을 요구. 섞어 적용하면 나중 것이 이김
